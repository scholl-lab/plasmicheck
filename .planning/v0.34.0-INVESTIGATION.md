## Issue #75: Some xDNA Files Don't Work

### Status: Cannot Reproduce — Needs User Input

**Issue body is empty.** No reproduction steps, no failing files, no error messages.

### What We Found

- All 9 existing `.xdna` files in `reference/plasmid/` parse and convert successfully
- Full pipeline flow (xDNA → GenBank → FASTA) works for all files
- BioPython 1.85's `XdnaIO` only supports version 0 of the xDNA format; version != 0 raises `ValueError: Unsupported XDNA version`
- `.xdna` (Serial Cloner / DNA Strider) and `.dna` (SnapGene) are **different binary formats**. BioPython supports both via separate parsers (`xdna` vs `snapgene`)

### Identified Potential Failure Modes

| Failure Mode | Cause | Fix |
|---|---|---|
| `Unsupported XDNA version` | File created by newer DNA Strider/Serial Cloner with version > 0 | Better error message + suggest converting via SnapGene |
| SnapGene `.dna` misidentified as `.xdna` | User renames `.dna` → `.xdna` | Auto-detect format via magic bytes (SnapGene starts with `\x09\x00\x00\x00\x0E SnapGene`) |
| Problematic FASTA header from xDNA | Record ID becomes `[author` (bracket + truncated comment) | Override record ID with sanitized filename |
| No CDS features in xDNA | Some xDNA files may lack feature annotations | Already handled (xDNA → FASTA doesn't require features) |

### Recommended Action

1. **Ask the issue reporter for the failing xDNA file** — comment on #75 requesting reproduction data
2. **Add format auto-detection**: check magic bytes to distinguish xDNA vs SnapGene `.dna`
3. **Add SnapGene `.dna` support** (BioPython already has `snapgene` parser — just wire it up)
4. **Override xDNA record ID** with the sanitized filename (not the truncated comment field)
5. **Better error messages** for unsupported xDNA versions

**Complexity:** Low-Medium (mostly defensive improvements)
**Effort:** 1-2 days

## Issue #68: Normalize by Splice Junction Count

### Scientific Rationale

The contamination ratio (`plasmid_reads / human_reads`) is biased by the number of splice junctions in the insert gene:
- **Multi-exon genes**: More junction-spanning reads → easier to classify as human → lower ratio
- **Single-exon genes**: No junction-spanning reads → harder to classify → ratio appears higher

Normalization would make ratios comparable across plasmids carrying different genes.

### What's Already Available

The spliced alignment BAM (`spliced_alignment.bam`) already exists for every combination. The CIGAR `N` operations represent introns/splice junctions. Currently, this BAM is only used to extract spanned genomic regions and cDNA positions — **splice junction count is NOT extracted**.

### Recommended Phased Approach

**Phase 1 — Extract + report (low risk):**
- Count `N` operations in spliced BAM CIGAR → store `SpliceJunctionCount` + `ExonCount` in `cDNA_positions.txt` and `summary.tsv`
- Report alongside ratio (purely informational)
- No threshold changes

**Phase 2 — Optional normalization (medium risk):**
- Compute `normalized_ratio` alongside `raw_ratio`
- Config flag to choose which drives the verdict (default: raw for backward compat)
- Both reported in outputs

**Phase 3 — Calibration (high effort):**
- Validate against known samples with varying junction counts
- Calibrate normalized thresholds

### Pitfalls

- Single-exon genes have 0 junctions — need `+1` offset or special handling
- Plasmids with no human homolog → concept doesn't apply
- Changing ratio scale invalidates current thresholds (0.8 contaminated, 0.6-1.0 unclear)
- Alternative splicing: cloned isoform ≠ all possible isoforms

**Complexity:** Medium (Phase 1), High (Phases 2-3)
**Effort:** Phase 1: 1-2 days, Phase 2: 2-3 days, Phase 3: 3-5 days

## Issue #39 + #43: Cross-Run Index and Spliced Alignment Caching

### The Problem

Every `sample × plasmid` combination creates its own copies of:
- Plasmid FASTA, MMI, FAI (identical across samples for the same plasmid)
- Spliced alignment BAM, spliced reference FASTA/MMI/FAI, cDNA positions (identical across samples)

**Verified**: `pcDNA5_FRT_TO_KCNJ5.fasta` has MD5 `e20839636ee` in both sample dirs; `spliced_reference.fasta` has MD5 `ffeddfa7f44` in both. Byte-identical files rebuilt from scratch each time.

### Existing Within-Run Dedup

v0.32.0 added `PipelinePlan.built_indexes` set — but it **only tracks the human reference index**. Plasmid indexes and spliced alignments have **no dedup** even within a single run.

### Proposed Cache Architecture

```
~/.plasmicheck/cache/
  version
  indexes/<md5_hex[:2]>/<md5_hex>/
    manifest.json
    index.mmi, index.fasta.fai
  spliced/<compound_key[:2]>/<compound_key>/
    manifest.json
    spliced_alignment.bam (+.bai)
    spliced_reference.fasta (+.fai, .mmi)
    cDNA_positions.txt
```

- **Cache key**: MD5 of plasmid FASTA (fast — files are ~6 KB)
- **Manifest**: records tool versions (minimap2, samtools), plasmicheck version, input hashes
- **Invalidation**: content-addressed (MD5 of inputs is the key) — old entries never "invalid", just unused
- **Locking**: extend existing `filelock` pattern to cache entries
- **CLI**: `--cache-dir`, `--no-cache`, `plasmicheck cache info|clean`

### Disk Impact

~150 KB per plasmid (index) + ~175 KB per plasmid (spliced). For 50 plasmids: ~16 MB total. Negligible.

### Implementation Plan

**Phase 1 (#39): Plasmid index caching**
- New `plasmicheck/cache.py` module (~250 lines)
- Extend `built_indexes` to cover plasmid indexes within-run (low-hanging fruit)
- Cross-run cache lookup + populate
- `--cache-dir` + `--no-cache` flags

**Phase 2 (#43): Spliced alignment caching**
- Extend `CacheManager` for spliced artifacts
- Compound cache key: `md5(plasmid) + human_ref_id + padding`
- Higher impact — spliced alignment runs minimap2 against 6.8 GB human index

**Complexity:** Medium (Phase 1), Medium-High (Phase 2)
**Effort:** Phase 1: 2-3 days, Phase 2: 2-3 days
